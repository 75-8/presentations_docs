# 製造業では「便利だから使う」だけでは進まない

- 機密情報を扱う
- 情報流出を避ける必要がある
- 利用者を管理する必要がある
- 利用状況を確認できる必要がある
- それでも **コストは抑えたい**

<!--
製造業では、AIが便利だからといって自由に使えるわけではない。

特に重要なのが機密情報。
コードや設計情報など、社外に出したくない情報を扱う可能性がある。

そのため、AI活用を進めるには、
セキュリティやガバナンスをクリアする必要がある。

一方で、製造業ではコストも重要。
高額なサービスを導入すれば解決、というわけにもいかない。

この「安全に使いたい」と「安く使いたい」の両立が今回の出発点だった。
-->

---

# そこでCoding Agentを「社内で使える環境」にしてみた

```text
Coding Agent
     │ Entra ID / Bearer Token
     ▼
   Azure APIM
     │ Managed Identity
     ▼
 Azure AI Foundry
     │
     ▼
    LLM
```

<!--
今回、クライアントとしてCoding AgentのCodexを利用した。

LLMへ直接接続するのではなく、APIMを間に置いた。

ユーザーからはEntra IDのBearer Tokenで認証する。

APIMからFoundryへの接続はManaged Identityを利用する。

こうすることで、ユーザーにAPIキーを配布する必要をなくした。
-->

---

# 「誰が使っているか」を管理するためにAPIMを置くことにした

* Entra IDでユーザーを認証
* JWTからユーザーを識別
* APIM Policyで利用者を制御
* ホワイトリスト／ブラックリストによる追加制御
* 接続元・利用条件もPolicyで制御

<!--
Foundryに直接接続するだけでは、
今回必要としていた利用者単位のコントロールが難しかった。

そこでAPIMを制御点として置いた。

Entra IDのBearer TokenをAPIMで検証し、
JWTからユーザーを識別する。

その情報を利用して、誰が使ってよいか、
逆に誰を使わせないかをPolicyで制御できるようにした。

APIキーをユーザーに配布しなくてよいことも重要なポイントだった。
-->

# ところが、最初のAPIMではログが取れなかった

## Consumption SKUという落とし穴

```text
「APIMを置けばログを取れる」
          ↓
       実際には？
          ↓
   SKUによる機能差
          ↓
 Consumptionでは想定した
 監視・ログ機能が使えない
```

<!--
ここが今回の最初の大きなつまずき。

APIMを使ってユーザー管理をしようとしたが、
利用状況を確認するためのログについて調べていくと、
SKUによって利用できる機能に差があることが分かった。

特にConsumption SKUで想定していた監視・ログの構成が成立しなかった。

Microsoft Learnだけでは判断できず、
一般のブログなどにも異なる情報があり、
「使えるのか、使えないのか」を確認すること自体に時間がかかった。

最終的には実際にAzure上で構築して試すことで、
成立する構成を確認していった。
-->

# 情報を集めるより「小さく作って試す」

```text
調べる
  ↓
仮説を立てる
  ↓
最小構成で作る
  ↓
実際に動かす
  ↓
結果を見る
  ↓
設計を修正する
```

<!--
今回の経験で強く感じたこと。

Azureの機能について調べても、
自分が実現したい構成で本当に動くのかまでは分からないことがある。

特にAzureはSKUやプレビュー機能などによって条件が変わる。

そのため、ある程度調べたら、
小さな構成を実際に作って試す方が早かった。

ただし、何も考えずに試すのは危険。
特にクラウドは設定によって想定外のコストが発生する可能性がある。
-->

---

# 「作って試す」には、先にガバナンスが必要だった

```text
        作って試す
            │
     ┌──────┴──────┐
     ▼             ▼
 セキュリティ      コスト
     │             │
     ▼             ▼
認証・権限       利用量監視
利用者制御       予算管理
ネットワーク     ログ
```

<!--
ここが今回の重要な学び。

作って試すことは有効だったが、
クラウド環境では「とりあえず作る」が危険でもある。

特に今回のように、インフラ経験がない状態でAIのサポートを受けながら作る場合、
設定ミスによるセキュリティ事故や想定外の請求は避けなければならない。

だから、試行錯誤するためにも、
認証、権限、利用者制御、コスト監視などのガードレールを先に考えた。
-->

# 最終的に「使った量」まで見えるようにした

```text
APIM
 │
 ▼
Application Insights
 │
 ├─ メトリック
 │      └─ 利用量を可視化
 │
 └─ ログ
        │
        ▼
   Blob Storage
        │
        ▼
     Power BI
```

<!--
最終的には、誰がどれくらい利用しているかを確認できるところまで作った。

Application Insightsのメトリックを利用して、
一定期間の利用状況をダッシュボードから確認できるようにした。

さらにログをBlob Storageへエクスポートして、
Power BIからローカルで分析できるようにした。

「誰が」「どれだけ」「何に使ったか」を確認できることを目指した。

AIを使えるだけではなく、使った後に管理できる状態を作ることを意識した。
-->

# 未経験者でも作れる。でも「AIに任せれば安全」ではない

## AIは実装を加速できる

## しかし、判断とガバナンスは残る

<!--
AIによって、インフラ未経験者でもかなりのところまで実装できた。

一方で、AIが提示した構成をそのまま採用すればよいわけではない。

特にクラウドインフラでは、
セキュリティやコスト、権限設計を間違えると影響が大きい。

「AIに聞けば作れる」と「安全に運用できる」は別の問題だった。

ここは今回の経験から得た重要なポイント。
-->

# 今回の経験から得た3つの学び

### 1. AI活用の前に「使える環境」を作る必要がある

認証・権限・監視・コスト・ログまで含めて考える。

### 2. 情報収集だけではなく、実際に作って試す

Azureのような複雑なサービスでは、実環境での検証が早い。

### 3. 未経験者でもAIと一緒に作れる

ただし、ガバナンスとレビューの仕組みは必要。

<!--
今回の経験を3つにまとめる。

一つ目は、AIを導入するだけではなく、
組織として安全に使える環境を作る必要があること。

二つ目は、情報を調べ続けるより、
安全な範囲で実際に作って試すことが有効だったこと。

三つ目は、インフラ未経験者でもAIのサポートによって
かなり高度な構築まで到達できたこと。

ただし、それはAIに全部任せればよいという意味ではない。
-->
